从频繁报错到稳定出图：我给 ComfyUI 插件的云 API 节点做了一次全面体检

一句话摘要：我把自己的 ComfyUI 插件 comfyui_bozo 里三个云 API 出图模块（BizyAIR、ModelScope、柏拉图AI）从"三天两头报错"修到了"稳定出图"，顺手新增了 2 个出图节点，全程只动 Python，不花钱。

写在前面

我自己重度使用 ComfyUI 做 AI 绘图工作流，前段时间DeepSeek-V4.1-Flash 发布，我就第一时间接入了魔搭社区的LLM节点。

当然，插件节点包里也有少不少VLM的节点

特别是方便的出图接口：BizyAIR、魔搭 ModelScope、柏拉图AI（apilio.ai）。用得多了问题就来了——

  • BizyAIR 的节点十次里有两三次下载结果图直接报 SSLError(SSLEOFError)，更气人的是有时候明明生成了 4 张图，最后输出却是空白；
  • 魔搭的节点跑着跑着突然就不出图了，日志里翻半天也找不到原因；
  • 长任务一跑就是几分钟，终端黑着没任何输出，根本不知道它是死了还是在干活。

这次我下决心把这些节点全部梳理了一遍：一边排查修复老问题，一边把几个只写了命令行脚本的能力（BizyAIR 的 gpt-image-2、柏拉图AI 的 GPT-image-2）封装成了正式的节点面板。这篇文章就是把整个修改思路完整复盘出来，每个问题都带真实报错和定位过程，希望同样在写 ComfyUI 插件的朋友能少踩坑。

效果先看

修完之后达到的效果：

  • SSL 中断自愈：结果图下载偶发中断时自动重试，不再丢图、不再输出空白图；

第一步：修复 BizyAIR 下载 SSL 中断与丢图 bug

做什么：让结果图下载失败时自动重试，并修掉"下载失败导致全部丢图"的连锁 bug。

怎么做：先看真实报错，日志里是这样的：

❌ 加载图像失败: HTTPSConnectionPool(host='storage.bizyair.ai', port=443):
   Max retries exceeded ... SSLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING]'))

更隐蔽的是后面这个 bug：第一张图下载失败后，老代码返回了一张 64×64 的占位图；合并多张图时逻辑是"以第一张的尺寸为基准过滤"，结果后面 3 张下载成功的图全被当成"尺寸不匹配"丢掉了，最终输出空白。看到这行日志就能确认：

⚠️ 警告: 忽略了 3 张尺寸不匹配的图像
✅ 合并了 1 张图像，最终形状: torch.Size([1, 64, 64, 3])

修复分三处：

# 1. 统一带重试的请求函数，遇到 SSL 中断自动重试 3 次（3s→6s→9s 退避）
def _request_with_retry(method, url, **kwargs):
    last_err = None
    for attempt in range(1, MAX_RETRIES + 1):
        try:
            resp = requests.request(method, url, **kwargs)
            resp.raise_for_status()
            return resp
        except requests.RequestException as e:
            last_err = e
            if attempt < MAX_RETRIES:
                time.sleep(RETRY_BACKOFF_SEC * attempt)
    raise last_err

# 2. url_to_tensor 失败时返回 None，调用方直接跳过（不再返回占位图）
# 3. 合并时只拼接尺寸一致的张量，异常图天然被排除

预期看到什么：偶发 SSL 中断时终端多一两条「⚠️ 请求异常（第 1 次），3 秒后重试」，随后正常出图；4 张图全部成功合并为 torch.Size([4, 1664, 960, 3])。

第二步：封装 BizyAIR GPT-I2 出图节点

做什么：把只在命令行里能用的 gpt-image-2-channel 接口封装成正式节点。

怎么做：照着我那份能跑通的 CLI 脚本还原完整流程——提交任务、等 40 秒、每 5 秒轮询一次、超时 1200 秒、下载结果。节点面板设计成：

"required": {
    "prompt": ...,                          # 提示词
    "aspect_ratio": (GPT_I2_ASPECT_RATIOS), # 15 种比例
    "resolution": (["1k", "2k", "4k"]),     # 分辨率，默认 4k
},
"optional": {
    "image": ("IMAGE",),                    # 参考图，有值自动走图生图
    "image_urls": ...,                      # URL 每行一个，最多 10 张
    "api_key": ...,                         # 留空读 key 文件
}

本地张量参考图的上传走两步：先 GET /v1/upload/token 拿 STS 临时凭证，再用 alibabacloud_oss_v2 传到阿里云 OSS，拿到公网 URL 再提交任务。

预期看到什么：重启 ComfyUI 后节点面板 🇨🇳BOZO/BizyAir 分类下出现「GPT图像生成（BizyAIR）」，跑一次文生图约 1~3 分钟返回图像。

第三步：终端读秒 + 直连加固

做什么：长任务等待期间终端不再"黑屏"，并进一步压缩 SSL 中断的发生概率。

怎么做：写了一个后台线程读秒器，每秒在终端同一行覆盖刷新（\r 回行首是实现动态刷新的关键）：

class ElapsedTimer:
    def _run(self):
        for i in itertools.count(1):
            if self._stop_event.is_set():
                break
            mins, secs = divmod(i, 60)
            print(f"\r⏳ {self.label}... 已等待 {mins:02d}:{secs:02d} (分:秒)   ",
                  end="", flush=True)
            self._stop_event.wait(1)

直连加固则是在每次请求时新建 Session 并设 trust_env=False，同时加 Connection: close 请求头不复用旧连接，重试次数提到 5 次。

预期看到什么：跑长任务时终端每秒跳动「⏳ BizyAIR 任务执行中... 已等待 00:37 (分:秒)」，结束后自动换行输出结果日志。

第四步：排查 401，揪出 Fake-IP 代理这个真凶

做什么：搞清楚为什么修完网络还是偶发 401。

怎么做：这是我这次排查里最有意思的一段。401 的字面意思是"鉴权失败"，第一反应是 key 失效——但同一个 key 有时能过有时不能。我用 curl 和 dig 逐层排查：

$ dig +short api.bizyair.ai
198.18.0.28        # ← 可疑！

198.18.x.x 是保留网段，正常公网解析不可能返回它。这是 Clash/Surge 这类代理工具 TUN/Fake-IP 模式的标志性地址——也就是说我的系统代理在网络层接管了全部流量，代码里设 NO_PROXY、trust_env=False 都绕不过去（它们只能管应用层的代理环境变量）。用阿里 DoH 拿真实 IP 一对比就清楚了：

$ curl -s "https://223.5.5.5/resolve?name=api.bizyair.ai&type=A"
# 真实 IP：104.18.20.64 / 104.18.21.64（Cloudflare）

预期看到什么：确认根因后，在代理客户端加一条直连规则 DOMAIN-SUFFIX,bizyair.ai,DIRECT，SSL 中断和 401 基本绝迹。这个坑代码层无解，必须改代理配置。

第五步：兼容 webapp 接口的新返回格式

做什么：让老节点能解析平台改版后的返回结构。

怎么做：任务查询接口的 outputs 字段从「列表 + object_url 字段」变成了「按类型分组的字典」，长这样：

"outputs": {
  "images": ["https://storage.bizyair.ai/outputs/xxx.png"],
  "videos": [], "texts": [], "audios": [], "meshes": [], "archives": []
}

我把解析逻辑归一化：字典格式按类别映射扩展名（images→图片、videos→mp4、texts/audios→文本），再按 URL 实际扩展名兜底；旧的列表格式原样保留兼容。这样平台以后再改回旧格式也不会挂。

预期看到什么：webapp 任务完成后，image / mp4 / txt 各输出口都能正常拿到对应内容。

第六步：对照可用实现修复魔搭节点

做什么：让魔搭三个出图节点（PicRun、多 LoRA 文生图、多 LoRA 图生图）恢复出图。

怎么做：方法论还是"拿能跑的对照不能跑的"。我手里有一份实测可用的魔搭 MCP server 代码，逐字段对比后发现两处关键差异：

# 老节点（跑不通）                    # MCP（能跑通）
payload = {"scale": guidance, ...}    payload = {"guidance": guidance, ...}
"image_url": [url1, url2]             "image_url": url1            # 单张传字符串
"loras": {id: 1.0}                    "loras": "model_id"          # 单个传字符串

修复策略：引导系数 guidance 和 scale 双字段同发（后来发现我另一份批量脚本用的就是 scale，说明新旧字段平台都认，双发最稳）；单张图/单 LoRA 传字符串，多张才传列表；seed=-1 在客户端直接生成随机数并打印实际值，方便复现。

预期看到什么：节点正常返回图片，image_url 输出可访问的结果链接。

第七步：吸收批量脚本的工程经验

做什么：把我另一份"实战中反复打磨过"的多 Key 批量出图脚本里的机制搬进节点。

怎么做：这份脚本每天要跑几百个任务，它的 Key 管理策略明显更成熟，我挑了四条搬过来：

脚本机制节点落地方式
prompt 截断 1900 字符（魔搭上限 2000）三个节点提交前统一截断
401 永久标记死 keykey 池新增 mark_dead()，失效 key 退出轮询
429 限流换 key 立即重试提交遇 401/429 自动切下一个 key
首次轮询前等 10~20 秒减少提交后立刻查询的无效请求

另外还发现脚本会把 output_images 里的所有图都下载，而老节点只取第一张——也顺手改成了多张合并 batch 输出。

预期看到什么：某个 key 被平台禁用后，日志出现「key …xxxxxx 已标记失效(401)，剩余 N 个可用」，任务自动用下一个 key 跑完，不需要人工干预。

第八步：新增柏拉图AI 出图节点

做什么：把柏拉图AI（apilio.ai）的 GPT-image-2 CLI 也封装成节点。

怎么做：和第二步同一套思路，但这个接口是同步的——一个请求挂 90 秒到 10 分钟才返回。所以重点是把 CLI 里现成的动态读秒计时器直接复用进来，避免长等待期间终端无输出。key 读取 key/bltcy.txt，支持多 key 轮询和自动回写保存。

预期看到什么：节点面板出现「柏拉图图像生成~ 🎯BOZO」，执行期间终端读秒跳动，最终返回图像和 URL。

踩坑记录

Q1：SSL 中断到底是谁的锅？ 分两层。应用层：requests 会读 macOS 系统代理，trust_env=False + NO_PROXY 能管住；网络层：TUN/Fake-IP 模式的代理在网络层截流，代码无解，只能在代理客户端加直连规则。遇到"怎么改代码都不行"的网络问题，先 dig 一下域名，看到 198.18.x.x 就直接去查代理。

Q2：明明生成了 4 张图，为什么输出是空白？ 老代码下载失败时返回 64×64 占位图，而合并逻辑以"第一张的尺寸"为基准过滤，第一张恰好是占位图时，后面所有正常图都被丢掉。教训：错误状态不要伪装成正常值往下游传，返回 None 让调用方跳过更安全。

Q3：ComfyUI 节点的 IS_CHANGED 报 missing self？ ComfyUI 是以类方法形式调用 IS_CHANGED 的，定义必须写成 def IS_CHANGED(*args, **kwargs):，不能写 self。这是 ComfyUI 插件的固定写法，跟普通 Python 类不一样。

Q4：节点字段到底该用 scale 还是 guidance？ 我一开始只按 MCP 改成 guidance，后来发现自己另一份每天在跑的批量脚本用的是 scale——说明平台两个都认。结论：有多个可用参照时，找它们之间的"公共兼容写法"（双字段同发），比赌单边更稳。

Q5：为什么终端读秒用 \r 而不是不断 print 新行？ ComfyUI 的终端日志很长，读秒如果每秒一行会把关键报错冲没。\r 回到行首覆盖刷新，一行始终只占一屏，结束后再 print() 换行把光标让出来。

小结

这次重构最大的收获是想清楚了一个方法论：修节点不要凭感觉改，先找一个"确认能跑通"的参照实现，逐字段逐请求地对照。BizyAIR 的 GPT-I2 节点是照 CLI 还原的，魔搭节点是照 MCP 修的，柏拉图AI 节点干脆和 CLI 共用同一份代码——参照物让每个决定都有依据。

不足也有：Fake-IP 代理的坑只能在客户端侧解决，插件本身没法自动检测；魔搭返回多张图时尺寸不一致的场景还没做缩放对齐。下一步我打算把三个云 API 节点的公共逻辑（重试、读秒、多图合并、key 轮询）抽成一个共享模块，新接平台时就能直接复用。
